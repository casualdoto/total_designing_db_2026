# Обоснование ограничений

## FOOD-108: помесячный финансовый отчёт

`how_much_money` — обычное представление с восемью колонками контракта FOOD-108:
`year_month text` в формате YYYY-MM, затем семь колонок numeric:
`sum_no_commission`, `sum_with_commission`, `commission`, `prev_commission`,
`commission_diff`, `courier_pay`, `net_profit`. Представление security_invoker
использует права вызывающего пользователя (PostgreSQL 15+); таблицы указаны
с полной схемой. SELECT не запускает расчёт зарплаты и ничего не изменяет.

Учитываются только доставленные заказы за всю историю, месяц определяется
по order_timestamp, как в FOOD-107. Сначала считается сумма позиций каждого
заказа `round(sum(quantity * unit_price), 2)` и комиссия
`round(сумма * 0.10, 2)` (BR-1.4/7.10). Потом агрегируются суммы без комиссии
и с комиссией по месяцу. Формулы совпадают с order_totals, но не требуют
обращений к payment, review или текущим ценам product.

WITH RECURSIVE создаёт календарь от первого до последнего месяца доставок
с шагом один месяц (BR-11.9). Если доставок нет, календарь и отчёт пусты,
даже при наличии выплат. Разрывы заполняются нулевыми суммами заказов.
Границы определяются только доставками, выплаты вне диапазона их не расширяют.
Выплаты суммируются отдельно по сохранённым year/month всех курьеров, затем
соединяются с календарём; отсутствие выплат означает 0. Агрегация до JOIN
не позволяет позициям и выплатам размножать друг друга.

Комиссия месяца — разность sum_with_commission и sum_no_commission.
LAG по полному календарю берёт комиссию предыдущего календарного месяца,
включая нулевые месяцы. Для первой строки prev_commission и commission_diff
равны NULL; в остальных commission_diff — разность текущей и предыдущей комиссий.
Чистая прибыль — commission минус фактическая сумма courier_pay.

**Принятое решение к проверке FOOD-108:** если в месяце без доставок
сохранена положительная выплата, она учитывается, а net_profit отрицателен.
Нулевая прибыль для месяца без доставок ожидается при нулевых выплатах.
Сохранённые выплаты не обнуляются ради проверки «месяц без заказов».

Представление читает актуальное состояние без REFRESH. Порядок вывода
задаётся внешним ORDER BY year_month. Установка — `10_how_much_money.sql`
перед grants.sql; существующие SQL-объекты не меняются.
Проверки под inspector — `db/check_how_much_money.sql`; протокол — `db/tests.md`.

## FOOD-107: зарплата курьеров

`courier_salary()` без параметров рассчитывает выплаты всем курьерам за текущий
календарный месяц сервера (BR-10.1/10.2). Доставленные заказы отбираются по
`order_timestamp >= начало месяца AND order_timestamp < начало следующего`,
как в генераторе и C.8 шаблона. Дата доставки не определяет месяц расчёта.
Другие статусы не участвуют (BR-10.5).

Сначала позиции сворачиваются до одного заказа: комиссия равна
`round(round(sum(quantity * unit_price), 2) * 0.10, 2)`, согласно `order_totals`.
Затем считаются количество заказов и сумма комиссий курьера. Историческая
`unit_price` не зависит от текущей цены блюда; несколько позиций не увеличивают
число доставок. Выплата равна `round(сумма комиссий * применённый коэффициент, 2)`.
Платежи и отзывы не читаются. Общий набор агрегатов используется для выплаты
и коэффициента, без повторного поиска заказов для каждого курьера.

**Принятое решение для повторного вызова:** если строка текущего месяца
уже существует, ставка берётся из её `coefficient_used` и сохраняется.
При отсутствии строки используется текущий `courier.coefficient`.
После первого расчёта поле курьера уже содержит ставку следующего месяца,
поэтому повторное чтение этого поля вместо сохранённой ставки изменило бы
зарплату ошибочно. Правило также согласует FOOD-107 с историей, созданной FOOD-102.
Повторный вызов обновляет только сумму через ON CONFLICT по существующему PK
`(year, month, courier_id)`; выплаты других месяцев не меняются (BR-10.3).

Работающим назначается коэффициент следующего месяца: до 150 доставок — 0.1,
151–250 — 0.2, 251–500 — 0.3, свыше 500 — 0.5. Уволенные получают выплату,
но их коэффициент не обновляется (BR-10.6). Без доставок выплата равна 0,
коэффициент следующего месяца работающего — 0.1 (FOOD-107). Переполнение
`courier_pay.amount numeric(8,2)` возвращает штатную ошибку 22003; частичных
выплат или изменений коэффициентов не остаётся.

Процедура фиксирует массив UUID курьеров и блокирует строки FOR UPDATE
в порядке UUID. Расчёт идёт отдельным SQL-запросом после получения блокировок
для того же набора курьеров. При READ COMMITTED конкурирующий вызов ждёт,
затем видит уже сохранённую ставку месяца и пересчитывает выплату с ней.
Новому курьеру, появившемуся после фиксации набора, выплата создастся следующим
вызовом. Установка — `09_courier_salary.sql` перед `grants.sql`; SECURITY INVOKER,
фиксированный search_path, без COMMIT и вызовов других прикладных процедур.
Генератор остаётся независимым; ночное расписание не настраивается.
Проверки — `db/check_courier_salary.sql`; протокол — `db/tests.md`.

## FOOD-106: статистика по ресторанам

`get_statistic()` возвращает ровно пять колонок в порядке контракта BR-13.2:
`restaurant_name text`, `best_product_name text`, `total_amount numeric`,
`avg_amount numeric`, `best_user text`. На каждый UUID ресторана приходится
одна строка, независимо от совпадения названий и текущего статуса ресторана.
Учитываются только доставленные заказы за всю историю (FOOD-106).

Доставленные заказы и их позиции соединяются один раз, результат сохраняется
в MATERIALIZED CTE. Сумма заказа вычисляется как округлённая до копеек
`SUM(quantity * unit_price)`, комиссия — `round(сумма * 0.10, 2)`, итог —
сумма плюс комиссия, согласно BR-1.4/7.10 и представлению `order_totals`.
Цена берётся из исторической позиции, а не из текущей карточки блюда.
Сумма и среднее по ресторану считаются после свёртки до одной строки на заказ,
поэтому несколько позиций не размножают денежные суммы. Дополнительного
округления AVG нет; numeric результата не ограничивает суммарный оборот
размерностью столбцов отдельной позиции.

Популярность блюда — SUM(quantity), включая дробные значения; популярность
клиента — число доставленных заказов, не сумма покупок и не число позиций.
Группировка ведётся по UUID. Через MAX и JOIN отбираются только лидеры;
при равенстве выбирается случайный UUID из массива кандидатов по индексу
`1 + floor(random() * count(*))`. Названия и логин присоединяются после выбора.
`best_user` — `client.login`, согласно BR-2.6 и уточнению FOOD-106.

По согласованному решению для ресторана без доставок обе денежные колонки
равны 0, лучший клиент и блюдо — NULL. Пустая схема даёт пустую таблицу.
Функция VOLATILE из-за random(), SECURITY INVOKER, с фиксированным search_path;
порядок строк не гарантируется. Она только читает данные.

BR-11.8 обеспечивается структурой запроса: базовые order/order_structure
читаются одним JOIN, последующие проходы идут по промежуточным наборам.
Нет циклов по ресторанам, коррелированных подзапросов, LATERAL и оконных функций;
payment/review не читаются, новые индексы для подмены оптимизации не добавляются.
Использование `order_totals` здесь потребовало бы лишней работы со статусом
оплаты; вместо этого воспроизводится его денежная формула.

Установка — `08_get_statistic.sql` перед `grants.sql`. Проверки под inspector —
`db/check_get_statistic.sql`: контрольные суммы, лидеры, пустые данные и EXPLAIN
реального тела функции на генерации с 1000. Протокол — `db/tests.md`.

## FOOD-105: пересчёт рейтинга

`rating_change() RETURNS trigger` вызывается строковым триггером
`review_rating_change` после INSERT, UPDATE и DELETE на `review` (BR-9.6/9.7).
На INSERT пересчитывается новая сущность, на DELETE — прежняя, на UPDATE — обе
пары `(entity_type, entity_id)`, без повторного пересчёта одинаковой пары.
Изменение текста или фотографии также запускает пересчёт.

Для блюда/ресторана рассчитывается `round(avg(review.rating), 2)` по всем
отзывам соответствующего типа и ID. При отсутствии отзывов AVG возвращает NULL,
который сохраняется в агрегате (BR-9.7). Отзывы на заказ не имеют агрегата;
при переходе между типами очищается/обновляется прежний агрегат и вычисляется
новый. Точность совпадает с существующими `numeric(3,2)`.

Начальный рейтинг из FOOD-104 разрешён до изменений отзывов. Первый отзыв
заменяет его фактическим средним; после удаления последнего отзыва сохраняется
NULL, начальное значение не восстанавливается. Установочный скрипт не меняет
существующие рейтинги массово.

Перед вычислением средних функция блокирует затронутые строки родителей
через `FOR NO KEY UPDATE` в порядке типа и UUID. Среднее читается отдельным
запросом после получения всех блокировок: при READ COMMITTED ожидавшая транзакция
видит уже зафиксированные отзывы другого заказа. Блокировки удерживаются до
конца транзакции. Это дополняет блокировку заказа из FOOD-101, поскольку разные
заказы могут содержать отзывы на одну сущность. При более строгих уровнях
изоляции возможен обычный конфликт сериализации, требующий повтора транзакции.

Индекс `review_entity_rating_idx(entity_type, entity_id)` поддерживает выборку
отзывов по агрегируемому объекту. Существующий UNIQUE начинается с order_id
и сохраняется без изменений. Функция работает с правами вызывающего пользователя
и фиксированным search_path; обновляет только rating родителей, поэтому не
вызывает рекурсию. Проверки допустимости объекта отзыва FOOD-101 не отключаются.
Отзыв и агрегаты изменяются и откатываются в одной транзакции.

Генератор не вызывает `rating_change` явно: сохраняется прямая вставка и
прямой расчёт рейтингов FOOD-102, существующий триггер срабатывает автоматически.
Очистка DELETE также пересчитывает рейтинги перед удалением родителей.
Установка — `07_rating_change.sql` перед `grants.sql`.
Проверки под inspector — `db/check_rating_change.sql`; результаты основного,
конкурентного и регрессионных прогонов описаны в `db/tests.md`.

## FOOD-104: добавление блюда

`add_product(p_restaurant_id uuid, p_product_category_id uuid, p_name text,
p_price numeric, p_rating numeric, p_status product_status, p_description text,
p_photo_url text DEFAULT NULL)` принимает все атрибуты блюда, кроме ID.
`product_id` получает существующий DEFAULT `exts.uuid_generate_v4()` (BR-11.1).
Значения передаются вызывающим кодом: случайная генерация по паттернам относится
к FOOD-102 и не применяется внутри `add_product`.

Ресторан и категория обязательны и должны существовать (BR-5.1). Процедура
использует действующие FK при INSERT, поэтому проверка корректна и при
конкурентном удалении родительской записи. Обработчик только `foreign_key_violation`
преобразует ошибки двух известных FK в сообщения с именем поля и переданным ID,
сохраняя SQLSTATE `23503`; неизвестная ошибка FK передаётся без подмены.

Название, цена, статус и описание обязательны (BR-5.2, BR-11.3): NULL отклоняется
с `23502`. Название имеет длину 1–100 символов согласно размерности таблицы
и правилу непустых строк из паттерна 2a; пустое название/описание отклоняется
с `23514`, слишком длинное название — с `22001`. Параметр названия имеет тип
`text`, чтобы проверить длину до записи и не допустить молчаливого усечения.
Текст сохраняется без обрезки, дополнения и нормализации пробелов.

Цена — конечное неотрицательное число, включая ноль (BR-5.3); рейтинг — NULL
либо конечное число от 0 до 5 (BR-5.4). Нарушение диапазона или специальные
числа NaN/Infinity отклоняются с `23514` до округления. Цена после округления
до двух знаков должна помещаться в `numeric(7,2)`, иначе возвращается `22003`.
Допустимые дробные значения округляет сама таблица до её точности.
Статус имеет существующий enum-тип (BR-5.5). Фотография необязательна и по
умолчанию NULL (BR-5.6); переданный URL сохраняется как есть, без сетевых запросов.

Процедура выполняется с правами вызывающего пользователя (`SECURITY INVOKER`),
фиксированным `search_path`, без COMMIT и вызовов других прикладных процедур.
При ошибке частичная строка не сохраняется; старые блюда не изменяются.
Установка — после существующих скриптов и перед `grants.sql`.
Проверки под `inspector`: `db/check_add_product.sql`, протокол — `db/tests.md`.

## FOOD-102/103: генерация и очистка

`insert_test_data(value int)` добавляет новый независимый набор без изменения
прежних строк (BR-11.7, FOOD-102). Значение должно быть положительным и позволять
вычислить `5 * value` в `int`; иначе SQLSTATE `22023` возникает до вставки.
Дополнительная таблица `legal_entity` получает `value` строк. Таблица связей
`client_address` получает `4 * value` строк: все клиентские адреса используются.
На ресторан приходится пять блюд, на заказ — от одной до пяти разных позиций.

Генерация строк следует паттернам 2a/2b из `samples/all_examples.sql`: случайная
33-символьная основа из алфавита, `repeat`, затем `substring` до длины
`1 + floor(random() * N)` для каждого свободного `varchar(N)`. Для каждого
адреса, клиента, блюда и заказа создаётся новая основа; связанные с ним текстовые
поля могут использовать одну основу, но выбирают длины отдельно. Ни готовых слов,
ни префиксов, ни UUID вместо текста нет. Для `transaction_id varchar(100)`
повторяется случайный MD5, поэтому достижимы также длины 33–100.
Описания `text` генерируются длиной 1–150 тем же способом. Коллизия уникального
значения приводит к новой генерации и повторному INSERT; адрес повторяется целиком.

Согласованные исключения из произвольной длины: ИНН — 10/12 цифр, ОГРН —
13/15, расчётный счёт — 20 цифр (BR-4.5, действующие CHECK). Телефоны —
случайные цифры длиной 1–11 без префикса. Пароль — `md5(random()::text)`
(BR-2.3). URL фотографии соответствует паттерну 2d; URL или NULL допустимы
по BR-5.6/9.3. Пример с email не применяется: у клиента этого атрибута нет
(BR-2.1/2.6), физическая схема не меняется.

Все новые UUID получаются через `exts.uuid_generate_v4()` (BR-11.1),
enum — через `enum_range()` с индексом от 1 до длины массива (BR-11.5).
Массивы хранят сгенерированные ID и технические данные, а не словари.
Обязательные бизнес-константы (10% комиссии, начальный коэффициент 0.1,
пороги BR-10.2, минимальная сумма) сохраняются; случайные значения их не заменяют.

Заказы и платежи имеют одинаковое количество строк, а каждому заказу обязательна
успешная оплата: поэтому генерируется ровно одна успешная попытка на заказ
(BR-8.1, BR-11.7). Суммы читаются из `order_totals` и `payment_details`,
автор отзыва — из `review_details`. Каждый отзыв относится к объекту своего
заказа. Рейтинги новых блюд и ресторанов рассчитываются прямым UPDATE по отзывам;
при отсутствии отзывов остаются NULL (BR-9.6/9.7).

Временной диапазон — пересечение последних 180 дней, последних шести месяцев
и шести календарных месяцев, включая текущий. Время сервера используется без
таймзоны (BR-11.2). Курьеры наняты в начале диапазона; увольнение генерируется
в текущем месяце, заказы и доставки не выходят за дату увольнения. Один курьер
гарантированно работает, один его заказ доставлен в текущем месяце (BR-6.6).

Для каждого нового курьера создаётся шесть строк `courier_pay`, включая нулевые
(BR-10.7, FOOD-102). Месяц определяется по `order_timestamp`, как в C.8 шаблона.
Расчёт начинается с коэффициента 0.1; выплата равна округлённому до копеек
произведению коэффициента этого месяца на сумму комиссий доставленных заказов.
Число доставок определяет коэффициент следующего месяца по BR-10.2.
После увольнения коэффициент замораживается; у работающего `courier.coefficient`
после генерации содержит значение следующего месяца. Существующие курьеры,
их коэффициенты и выплаты не изменяются. Прикладные функции и процедуры явно
не вызываются; существующие триггеры продолжают работать.

`erase_test_data()` удаляет данные всех 13 таблиц через DELETE в порядке FK,
включая юридические лица, и сохраняет объекты схемы (FOOD-103). Повторная очистка
допустима. Обе процедуры работают в транзакции вызывающего кода без COMMIT;
используется стандартный для схемы режим отложенных проверок заказов
`DEFERRABLE INITIALLY DEFERRED`. Если вызывающий код переключил их в IMMEDIATE,
перед генерацией или очисткой он должен вернуть DEFERRED.

Проверки: `db/check_test_data.sql`; порядок установки и протокол — `db/tests.md`.

## Ловушки

Здесь — не готовые решения, а **фиксация того, как ты решил** каждую ловушку. Преподаватель читает, чтобы понять ход мысли.

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
В payment добавлены type, transaction_id, transaction_timestamp и status
по BR-8.2. transaction_id — уникальный строковый ID провайдера (BR-8.3),
payment_id — собственный UUID. Данные карт не хранятся (BR-1.7/8.5).
Сумма читается из payment_details.amount. По BR-8.4 order_id → amount,
но order_id не ключ payment: у заказа несколько попыток. Хранение amount
в каждой попытке нарушало бы 3НФ. Отдельного сохраняемого amount нет:
равенство общей сумме заказа обеспечивается определением payment_details.
```

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

```
Тип оплаты хранится в payment.type (BR-8.6): разные попытки одного заказа
могут использовать разные способы. order_totals.pay_status вычисляется
из попыток (BR-8.7). Частичный UNIQUE запрещает второй успех, отложенный
триггер требует ровно один успех к COMMIT (BR-8.1). Внутри транзакции
возможны ожидание и ошибка.
```

### Ловушка 2: `order.address_id` — принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

```
FOREIGN KEY (client_id, address_id) REFERENCES
client_address(client_id, address_id) требует адрес из адресной книги
клиента заказа (BR-7.4). Смена клиента или адреса проверяется тем же FK.
```

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
Отложенный триггер сравнивает restaurant_id блюда и заказа. Проверки родительских
изменений защищают также смену ресторана блюда/заказа (BR-7.3).
restaurant_id в order_structure не повторяется. unit_price — историческая
цена покупки, независимая от текущей product.price.
Отложенные проверки обеих сторон переноса требуют непустой заказ
с итогом не меньше 1000 (BR-7.11/7.14). Суммы выводятся через order_totals,
поэтому независимого значения order_amount в базовой таблице нет.
```

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

```
Сохранена полиморфная ссылка entity_type + entity_id (BR-9.1). Обычный FK
не выбирает одну из трёх таблиц; триггер проверяет покупку блюда, совпадение
ресторана или entity_id = order_id для оценки заказа.
Удаление/перенос оценённой позиции и изменения родительских записей защищены.
client_id не хранится: order_id → client_id, но order_id не ключ review.
Автор доступен в review_details и определяется клиентом заказа (BR-9.2).
Проверка личности вызывающего клиента должна выполняться приложением:
в схеме нет сопоставления SQL-роли с клиентом сервиса.
UNIQUE (order_id, entity_type, entity_id) обеспечивает BR-9.5.
Пересчёт рейтингов реализован триггером review_rating_change и функцией
rating_change (FOOD-105); подробнее в разделе FOOD-105 выше.
```

### Межтабличные ограничения

Реализованы в `db/schema/03_business_constraints.sql` функцией
`check_order_integrity` и отложенными constraint-триггерами. Обычный `CHECK`
не подходит: правила зависят от других строк и таблиц.

| Правило | BR | Проверка |
|---|---|---|
| Непустой состав заказа | BR-7.14 | У существующего заказа есть хотя бы одна позиция. |
| Минимальная сумма | BR-1.8, BR-7.11 | Округлённая сумма позиций плюс округлённая комиссия 10% не меньше 1000 ₽. |
| Один ресторан | BR-7.3 | Ресторан каждого блюда совпадает с рестораном заказа. |
| Ровно одна успешная оплата | BR-8.1 | Триггер требует наличие успеха; частичный UNIQUE запрещает второй. |
| Отзыв на заказанный объект | BR-9.1, BR-9.2 | entity_id — ID самого заказа, его ресторана или блюда в его составе. |

Проверки выполняются при COMMIT, также их можно вызвать через
`SET CONSTRAINTS ALL IMMEDIATE`. Заказ, позиции и успешную оплату нужно
создавать внутри одной транзакции. При переносе позиции или оплаты проверяются
оба заказа; при смене ресторана блюда — все заказы с этим блюдом.
Удаление оценённой позиции также требует удаления или изменения отзыва.
Если сам заказ удалён в этой транзакции, его итоговые проверки пропускаются.

Изменения позиций, оплат и отзывов сериализуются записью родительской строки
заказа; позиция также блокирует смену ресторана блюда через `FOR SHARE`.
Это защищает проверки от конкурентных изменений. При конфликтах возможны
обычные для PostgreSQL ошибки сериализации или взаимоблокировки;
приложение должно повторять всю транзакцию.

Установка скрипта атомарна и проверяет ранее существующие заказы: при
некорректных данных установка откатывается, данные автоматически не изменяются.

```
[Своими словами: все неключевые атрибуты зависят от полного PK (2НФ);
нет транзитивных зависимостей (3НФ).

Особые случаи:
- order.commission = 10% от order_amount — вычисляемое. Что сделал и почему.
- order.total_amount = order_amount + commission — вычисляемое. Что сделал и почему.
- product.rating и restaurant.rating — агрегаты, поддерживаются триггером rating_change. Это осознанная денормализация для скорости чтения — обоснуй.
- review.entity_id + entity_type — полиморфизм. Не нарушает 3НФ, но требует обоснования (см. ловушку 4).]
```
