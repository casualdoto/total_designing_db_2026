## Ловушки

Здесь — не готовые решения, а **фиксация того, как ты решил** каждую ловушку. Преподаватель читает, чтобы понять ход мысли.

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
Добавлены поля type (payment_type), amount (numeric(14,2)), transaction_id
(varchar(100)), transaction_timestamp (timestamp) и status (payment_status).
BR-8.2 требует способ, сумму, внешний идентификатор, время и результат попытки.
transaction_id — строковый реквизит провайдера, а payment_id — UUID нашей сущности.
UNIQUE и NOT NULL на transaction_id реализуют BR-8.3. Данные карт не хранятся
по BR-1.7 и BR-8.5.

Платёжный триггер сверяет amount с order.total_amount (BR-8.4) и поддерживает
order.pay_status (BR-8.7). Частичный уникальный индекс запрещает второй успех,
а отложенные constraint triggers требуют ровно один успех к COMMIT (BR-8.1).
Поэтому заказ, позиции и успешную оплату создают в общей транзакции; состояния
без успешной попытки допустимы только до её завершения.
```

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

```
Способ оплаты хранится в payment.type. BR-8.6 относит его к отдельной попытке:
один заказ может иметь попытки с разными способами. В order хранится только
агрегированный pay_status, а отдельного поля способа оплаты нет.
```

### Ловушка 2: `order.address_id` — принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

```
Используется составной внешний ключ:
FOREIGN KEY (client_id, address_id)
REFERENCES khrestianovskii_food.client_address(client_id, address_id).

Целевая пара является PK client_address. Совпадение только address_id было бы
недостаточным: по BR-2.4 один адрес может использоваться разными клиентами.
Составной FK проверяет именно принадлежность адреса клиенту заказа по BR-7.4.
Прямые FK заказа на client и address также сохранены согласно ERD.
```

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
BEFORE-триггер order_product_restaurant_check при INSERT и изменении order_id
или product_id сравнивает restaurant_id заказа и блюда. Несовпадение отклоняется
по BR-7.3. Дополнительные триггеры на product.restaurant_id и order.restaurant_id
не допускают нарушения связи через изменение родительских записей.

restaurant_id в order_structure не повторяется: это исключает избыточный атрибут
позиции. unit_price хранит цену на момент заказа; изменение текущей product.price
не переписывает историю. Отложенные проверки требуют хотя бы одну позицию
и совпадение order_amount с round(SUM(quantity * unit_price), 2) по BR-7.10/7.14.
```

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

```
Сохранён полиморфизм entity_type + entity_id из ERD. Один обычный FK не может
условно ссылаться на product, restaurant или order, поэтому цель проверяет
BEFORE-триггер review_target_check по BR-9.1/9.2:
- блюдо должно присутствовать в позициях указанного заказа;
- ресторан должен совпадать с рестораном заказа;
- для оценки заказа entity_id должен равняться order_id.

Составной FK (order_id, client_id) на order(order_id, client_id) проверяет автора.
UNIQUE (order_id, entity_type, entity_id) ограничивает повторные отзывы по BR-9.5.
Удаление и перенос позиции с отзывом запрещены; изменение ресторана заказа
не может оставить отзыв связанным с другим рестораном.

rating_change пересчитывает средние для прежней и новой цели при изменении
отзыва и устанавливает NULL при удалении последнего отзыва (BR-9.6/9.7).
Оценка заказа не обновляет агрегаты продукта или ресторана.
```

## NOT NULL (только бизнес-обязательные)

Сюда — **только** те `NOT NULL`, которые нельзя объяснить очевидностью.

**Не дублируй:**
- PK (всегда NOT NULL по определению);
- FK на NOT NULL поле (очевидно, если родитель NOT NULL);
- поля из BR с явным «обязательно» — только если хочешь подчеркнуть, что это не случайность.

| Таблица | Столбец | BR | Обоснование |
|---|---|---|---|
| `review` | `entity_type`, `entity_id` | BR-9.1, BR-9.2, BR-11.3 | Полиморфная ссылка должна полностью определять объект оценки; обычного FK для этих полей нет. |
| `payment` | `transaction_id` | BR-8.2, BR-8.3, BR-11.3 | Каждая попытка имеет внешний ID; один UNIQUE без NOT NULL разрешил бы попытки без идентификатора. |

## Нормализация (3НФ)

Короткое обоснование, что все таблицы в 3НФ:

```
Справочники client, address, courier и product_category описывают собственные
сущности. Связи client_address и order_structure имеют составные ключи;
quantity и историческая unit_price относятся к полной паре заказ–блюдо.
В courier_pay сумма и применённая ставка описывают полный ключ год–месяц–курьер.
Категории, адреса, попытки оплаты и позиции вынесены в отдельные отношения.

order.commission и order.total_amount — хранимые вычисляемые поля по BR-1.4/7.10.
Они не редактируются независимо; сумма блюд сверяется с позициями отложенным
триггером. В физической схеме это явно сохранённые расчётные зависимости.

product.rating и restaurant.rating — агрегаты для чтения, предусмотренные ERD.
Их согласованность с отзывами поддерживает rating_change по BR-9.6/9.7;
NULL обозначает отсутствие отзывов. Аналогично order.pay_status хранится ради
контракта ERD и поддерживается платёжными триггерами по BR-8.7.

Пара review.entity_type/entity_id задаёт полиморфную ссылку: сама по себе она
не доказывает нарушения 3НФ, но требует проверки цели триггером (см. ловушку 4).
Отдельная зависимость review.order_id → review.client_id сохраняется в текущей
модели ради явной связи из ERD и проверки автора составным FK. order_id не является
кандидатным ключом review, поэтому документирование этой зависимости не позволяет
утверждать строгую 3НФ всей физической схемы. Это ограничение текущей модели;
изменение структуры таблиц в рамках заполнения документа не выполнялось.

Технические параметры выбраны по BR-11.6: login — 50 символов, улица и ФИО — 150,
```
